# Φάση 4.2C — Κρυπτογραφημένο backup/restore του Manager

**Ημερομηνία:** 22/11/2026  
**Κατάσταση:** εγκεκριμένη προδιαγραφή (απόφαση χρήστη 22/11/2026), **όχι υλοποίηση**.  
**Υλοποίηση:** ChatGPT (`gpt-dev`). **Έλεγχος:** Claude.  
**Βάση:** [phase4-2.md](phase4-2.md) §1, §5, §8. Το αρχείο αυτό εξειδικεύει το §5 («Backup, μεταφορά και λειτουργίες») και υπερισχύει σε ό,τι αφορά τη μορφή και τη ροή του backup.

## 1. Σκοπός και όρια

- Ένα **κρυπτογραφημένο αρχείο** που περιέχει ό,τι χρειάζεται για να συνεχίσει ο Manager σε **νέο υπολογιστή** χωρίς νέα εγγραφή των Clients: την ίδια ταυτότητα TLS, το ίδιο υπογεγραμμένο μητρώο και την υπόλοιπη κατάσταση.
- **Ο Manager τρέχει πάντα σε Windows στην παραγωγή** (απόφαση χρήστη 22/11/2026). Το Linux είναι μόνο μηχάνημα ανάπτυξης. Η υλοποίηση και η πραγματική δοκιμή στοχεύουν πρώτα σε Windows. Ο κώδικας μένει φορητός (ίδια tests σε Linux), αλλά **δεν** απαιτείται ειδική ροή επαναφοράς από Linux σε Windows.
- **Εκτός 4.2C:**
  - GUI backup/restore: έρχεται με το tab «Πιστοποιητικά» (βλ. §9).
  - Κρυπτογράφηση του κλειδιού TLS του Manager στον δίσκο με DPAPI: χωριστό μικρό PR **4.2C2** αμέσως μετά (βλ. §7).
  - Κύριος/Εφεδρικός, εξαγωγή/εισαγωγή μόνο μητρώου και επίλυση συγκρούσεων: **4.2D**.
  - Τα ίδια τα αρχεία MP3 δεν μπαίνουν στο κρυπτογραφημένο αρχείο (βλ. §5).

## 2. Τι περιέχει σήμερα

Ο **φάκελος δεδομένων Manager** είναι ο φάκελος του `--registry-file` (σήμερα `%USERPROFILE%\.school-intercom\`). Το πιστοποιητικό και το κλειδί TLS διαβάζονται από τα `--tls-cert` / `--tls-key` (συνήθως `...\.school-intercom\tls\`).

| Ενότητα | Αρχείο(α) | Υποχρεωτική | Αν λείπει στο restore |
|---|---|---|---|
| `tls_identity` | πιστοποιητικό + ιδιωτικό κλειδί TLS (PEM) | ναι | απόρριψη backup |
| `client_registry` | `clients-registry.json` (υπογεγραμμένο, αυτούσιο) | ναι | απόρριψη backup |
| `enrollment_pending` | `enrollment-pending.json` | όχι | κανένα εκκρεμές αίτημα |
| `last_seen` | `clients-last-seen.json` | όχι | «ποτέ» για όλους |
| `director_id` | `director.id` | όχι | νέα ταυτότητα discovery |
| `gui_settings` | `director-gui.json` | όχι | προεπιλεγμένα πλάτη |
| `media_manifest` | λίστα MP3 (όνομα, μέγεθος, SHA-256, ρόλος) | όχι | καμία αναφορά MP3 |

Δεν μπαίνουν: logs, `restore-journal.json`, φάκελοι `pre-restore-*`, `last-backup.json`, προσωρινά αρχεία.

### Μελλοντικές ενότητες (μόνο ως πλαίσιο, όχι στο 4.2C)

`scenarios`, `settings` (π.χ. κεντρική ένταση ανακοινώσεων, mute άλλων εφαρμογών), `schedules`, `client_updates` (η κεντρική ρύθμιση αυτόματων ενημερώσεων και το manifest του εγκεκριμένου πακέτου Client της Φάσης 5, με έκδοση και hash. Το ίδιο το πακέτο **δεν** μπαίνει, όπως και τα MP3). Κάθε νέα ενότητα προστίθεται με δικό της `schema` χωρίς αλλαγή της μορφής του αρχείου (§3).

## 3. Μορφή αρχείου

Όνομα: `sch-intercom-backup-YYYYMMDD-HHMM.sib`. Δομή:

```
"SIBK" (4 bytes) | μήκος κεφαλίδας (uint32 big-endian) | κεφαλίδα JSON (UTF-8) | ciphertext AES-256-GCM (με το tag 16 bytes στο τέλος)
```

**Κεφαλίδα (χωρίς μυστικά):**

```json
{"format": 1, "created_at": "2026-11-22T19:30:00Z", "app_version": "…",
 "kdf": {"name": "scrypt", "n": 131072, "r": 8, "p": 1, "salt": "<base64 16 bytes>"},
 "cipher": {"name": "AES-256-GCM", "nonce": "<base64 12 bytes>"}}
```

- **AAD = όλα τα bytes πριν από το ciphertext** (magic, μήκος, κεφαλίδα). Οποιαδήποτε αλλαγή στην κεφαλίδα αποτυγχάνει στην αποκρυπτογράφηση.
- Νέο τυχαίο `salt` και `nonce` (`os.urandom`) σε **κάθε** backup.
- Η κεφαλίδα δεν περιέχει school_id, ονόματα αιθουσών ή αποτυπώματα. Ό,τι αναγνωρίζει την εγκατάσταση βρίσκεται μέσα στο κρυπτογραφημένο μέρος.

**Αποκρυπτογραφημένο περιεχόμενο:** ένα JSON (όχι ZIP, ώστε να μην υπάρχουν διαδρομές αρχείων προς επικύρωση):

```json
{"manifest": {
   "backup_format": 1, "created_at": "…", "app_version": "…", "source_computer": "…",
   "school_id": "…", "registry_version": 15, "registry_hash": "…",
   "tls_fingerprint": "AB:CD:…",
   "sections": {"tls_identity": {"schema": 1, "sha256": "…"}, "…": {}}},
 "sections": {
   "tls_identity": {"schema": 1, "files": {"cert.pem": "<base64>", "key.pem": "<base64>"}},
   "client_registry": {"schema": 1, "files": {"clients-registry.json": "<base64>"}},
   "media_manifest": {"schema": 1, "folder": "…", "files": [
      {"name": "κουδούνι.mp3", "size": 123456, "sha256": "…", "role": null}]}}}
```

- Το `sha256` κάθε ενότητας υπολογίζεται επί της κανονικοποιημένης σειριοποίησης της ενότητας (ίδια `canonical()` με το μητρώο) και ελέγχεται στο restore.
- **Όριο μεγέθους:** 16 MiB για όλο το αρχείο. Το restore αρνείται μεγαλύτερο αρχείο πριν διαβάσει το περιεχόμενο.

**Κανόνες συμβατότητας:**

- `format` μεγαλύτερο από αυτό που υποστηρίζει η εφαρμογή → άρνηση με «Το backup δημιουργήθηκε από νεότερη έκδοση. Αναβαθμίστε πρώτα τον Manager.»
- Ενότητα που λείπει → προεπιλογή του πίνακα §2 (παλιό backup σε νεότερη εφαρμογή επαναφέρει ό,τι έχει).
- Άγνωστη ενότητα (από νεότερη έκδοση) → αναφέρεται («Αγνοήθηκε: scenarios») και αγνοείται.
- `schema` ενότητας νεότερο από το υποστηριζόμενο → υποχρεωτική ενότητα: άρνηση. Προαιρετική: αναφορά, παράλειψη, προεπιλογή.
- Παλαιότερο `schema` → μετατροπή στη νέα μορφή στη μνήμη, πριν από την εγγραφή.

## 4. Κρυπτογράφηση και κωδικός

- **KDF:** scrypt από τη `cryptography` (ήδη υποχρεωτική εξάρτηση), `n=2^17, r=8, p=1`, κλειδί 32 bytes (περίπου 128 MiB μνήμη, κάτω από 1 δευτερόλεπτο σε σχολικό PC). Οι παράμετροι γράφονται στην κεφαλίδα ώστε να μπορούν να αλλάξουν αργότερα. Στο restore γίνονται δεκτές μόνο τιμές μέσα σε όρια (`2^15 ≤ n ≤ 2^20`, `r = 8`, `1 ≤ p ≤ 4`), ώστε ένα πειραγμένο αρχείο να μη γονατίσει τον υπολογιστή.
- **AEAD:** AES-256-GCM (`AESGCM`) με AAD όπως στο §3.
- **Κωδικός (passphrase):**
  - τουλάχιστον **12 χαρακτήρες**, πληκτρολογείται **δύο φορές** στο backup·
  - κανονικοποίηση Unicode **NFC** και UTF-8 πριν από το KDF, ώστε ελληνικοί τόνοι να δίνουν το ίδιο αποτέλεσμα σε κάθε πληκτρολόγιο·
  - δεν αποθηκεύεται, δεν εμφανίζεται, δεν γράφεται σε log ή σε command line·
  - διαβάζεται με `getpass`. Μόνο για τα αυτόματα scripts: κρυφή επιλογή `--passphrase-env ONOMA` (όπως το `--max-pending-requests`), που διαβάζει τον κωδικό από μεταβλητή περιβάλλοντος.
- Λάθος κωδικός και αλλοιωμένο αρχείο δίνουν **το ίδιο** μήνυμα: «Λάθος κωδικός ή αλλοιωμένο αρχείο. Ελέγξτε και τη γλώσσα του πληκτρολογίου.» Δεν γράφεται τίποτα στον δίσκο.
- Το backup λέει ρητά: «Χωρίς τον κωδικό το backup δεν ανοίγει. Φυλάξτε τον χωριστά από το αρχείο.»

## 5. MP3

- Οι **2 προεπιλεγμένοι ήχοι** (έναρξη/λήξη ανακοίνωσης) έρχονται με την εφαρμογή και **δεν** μπαίνουν στο backup. Αν ο χρήστης τους αντικαταστήσει, το αρχείο αντικατάστασης βρίσκεται στον φάκελο MP3 και καταγράφεται στο `media_manifest` με `role: "announcement_start"` ή `"announcement_end"`.
- Όλα τα άλλα MP3 βρίσκονται στον **φάκελο MP3** που ορίζει η εφαρμογή. Στο 4.2C: επιλογή `--media-dir`, προεπιλογή `<φάκελος δεδομένων>\media`. Αν δεν υπάρχει, το manifest είναι κενό. Η ρύθμιση του φακέλου από το GUI έρχεται με τη φάση σεναρίων.
- **Στο backup:** το `media_manifest` κρατά όνομα, μέγεθος και SHA-256 κάθε αρχείου (χωρίς υποφακέλους στο 4.2C). Αν ο φάκελος έχει αρχεία, εμφανίζεται:
  «Ο φάκελος MP3 έχει N αρχεία (X MB), που δεν μπαίνουν στο κρυπτογραφημένο backup. Να γίνει και αντίγραφο του φακέλου δίπλα στο backup; [Ν/ο]»
  Για scripts: `--media-copy ask|yes|no` (προεπιλογή `ask`).
- **Εξωτερικό αντίγραφο:** φάκελος `<όνομα backup χωρίς .sib>-media\` δίπλα στο `.sib`. Απλή αντιγραφή, **χωρίς κρυπτογράφηση** (τα MP3 δεν είναι μυστικά). Μετά την αντιγραφή ελέγχεται το SHA-256 κάθε αρχείου.
- **Στο restore:** σύγκριση manifest με τον φάκελο MP3 του νέου υπολογιστή και αναφορά ανά αρχείο: «λείπει», «διαφέρει» (ίδιο όνομα, άλλο hash), «επιπλέον» (υπάρχει μόνο τοπικά, ενημερωτικά). Με `--restore-media`, αν υπάρχει ο φάκελος `…-media\` δίπλα στο backup, αντιγράφονται **μόνο** τα αρχεία που λείπουν και έχουν το σωστό hash. Αρχείο που υπάρχει δεν αντικαθίσταται ποτέ.
- **Πλαίσιο για τη φάση σεναρίων (όχι 4.2C):** τα σενάρια θα δείχνουν αρχεία με hash + όνομα. Μετονομασμένο αρχείο ξαναβρίσκεται από το hash. Αν λείπει, ο χρήστης κάνει επανεισαγωγή ή επιλέγει αρχείο από τον φάκελο. Το `media_manifest` είναι η βάση για αυτό.

## 6. Ροές και εντολές (CLI)

Νέο module `director/backup.py`, εκτέλεση `python -m director.backup <εντολή>`. Όλες οι εντολές δέχονται `--registry-file`, `--tls-cert`, `--tls-key` με τις ίδιες προεπιλογές με το `director.main`.

| Εντολή | Τι κάνει |
|---|---|
| `create --out <φάκελος ή αρχείο> [--media-dir] [--media-copy]` | δημιουργεί backup |
| `inspect <αρχείο>` | χωρίς κωδικό: κεφαλίδα. Με κωδικό: σύνοψη manifest (ημερομηνία, υπολογιστής, έκδοση μητρώου, πλήθος Clients/αιτημάτων, αποτύπωμα TLS, ενότητες, MP3). **Ποτέ** κλειδιά ή πιστοποιητικά |
| `restore <αρχείο> [--replace-identity] [--accept-older] [--restore-media]` | επαναφορά |
| `rollback` | επιστροφή στην κατάσταση πριν από διακοπτόμενο restore |

**Κωδικοί εξόδου:** `0` επιτυχία, `2` λάθος χρήση ή μη έγκυρο περιεχόμενο, `3` λάθος κωδικός ή αλλοιωμένο αρχείο, `4` ο Manager τρέχει, `5` χρειάζεται ρητή επιβεβαίωση (`--replace-identity` / `--accept-older`).

### 6.1 Backup (`create`)

1. Ανάγνωση κάθε αρχείου **μία φορά** στη μνήμη. Τα αρχεία του Manager γράφονται ατομικά (`os.replace`), οπότε το backup επιτρέπεται και με Manager σε λειτουργία. Αν κάποιο JSON δεν διαβάζεται, μία επανάληψη και μετά σφάλμα.
2. Έλεγχοι πριν από την κρυπτογράφηση: το κλειδί ταιριάζει με το πιστοποιητικό, η υπογραφή μητρώου επαληθεύεται με αυτό το πιστοποιητικό (`verify_document`), τα προαιρετικά JSON είναι έγκυρα.
3. Κωδικός δύο φορές, KDF, κρυπτογράφηση στη μνήμη.
4. Εγγραφή σε `<προορισμός>.sib.tmp` **στον ίδιο φάκελο προορισμού** (π.χ. USB), `fsync`, `os.replace` στο τελικό όνομα. Δεν αντικαθίσταται υπάρχον backup. Στα Windows, `PermissionError` στο `os.replace` (antivirus) → έως 3 επαναλήψεις με 0,5 s αναμονή.
5. Προειδοποίηση αν ο προορισμός είναι μέσα στον φάκελο δεδομένων («Το backup είναι στον ίδιο δίσκο με τα δεδομένα. Προτιμήστε USB ή άλλο υπολογιστή.»). Δεν μπλοκάρει.
6. MP3 (§5).
7. Εγγραφή `last-backup.json` στον φάκελο δεδομένων: `{time, file_name, registry_version, registry_hash}`. Το tab «Πιστοποιητικά» θα δείχνει από εκεί «Τελευταίο backup» και «Αλλαγές μητρώου μετά το backup».

### 6.2 Επαναφορά (`restore`)

1. **Ο Manager δεν πρέπει να τρέχει.** Το `director.main` (CLI και `--gui`) κρατά κλείδωμα στο `<φάκελος δεδομένων>\manager.lock` όσο τρέχει (`msvcrt.locking` σε Windows, `fcntl.flock` σε Linux). Οι σύντομες offline εντολές `--approve-client-cert`, `--revoke-client` και `--list-clients` δεν κρατούν το κλείδωμα, επειδή τρέχουν και δίπλα σε ενεργό Manager· ελέγχουν μόνο το journal. Το restore παίρνει το ίδιο κλείδωμα και το κρατά ως το τέλος. Αν δεν το πάρει: «Ο Manager τρέχει. Κλείστε τον πρώτα.» (κωδικός 4).
2. Έλεγχος μεγέθους, ανάγνωση κεφαλίδας, όρια KDF, αποκρυπτογράφηση στη μνήμη.
3. Επικύρωση: `format`, hash κάθε ενότητας, κλειδί ↔ πιστοποιητικό, υπογραφή μητρώου με το πιστοποιητικό **του backup**, `school_id` του manifest ίδιο με του μητρώου, έγκυρα προαιρετικά JSON.
4. Σύγκριση με ό,τι υπάρχει ήδη στον υπολογιστή:
   - **Κενός υπολογιστής** → συνέχεια.
   - **Άλλη ταυτότητα TLS** (διαφορετικό αποτύπωμα) → κωδικός 5 χωρίς `--replace-identity`, με μήνυμα «Αυτός ο υπολογιστής έχει άλλη ταυτότητα Manager (AB:CD…). Οι Clients που είναι εγγεγραμμένοι σε αυτήν θα σταματήσουν να συνδέονται εδώ.»
   - **Ίδια ταυτότητα, τοπικό μητρώο νεότερο** (το hash του backup υπάρχει στο τοπικό `history`) → κωδικός 5 χωρίς `--accept-older`: «Το backup έχει παλαιότερο μητρώο (v12 < v15). Εγκρίσεις και ανακλήσεις μετά τη v12 θα χαθούν.»
   - **Σύγκρουση** (κανένα δεν υπάρχει στο ιστορικό του άλλου) → επίσης κωδικός 5 χωρίς `--accept-older`. Η συγχώνευση κλάδων είναι δουλειά της 4.2D.
5. **Ατομική εγκατάσταση με δυνατότητα επιστροφής:**
   - όλα τα αρχεία γράφονται πρώτα σε `<φάκελος δεδομένων>\.restore-staging-<ts>\` (το κλειδί με `_write_secret`, αποκλειστική δημιουργία), με `fsync`·
   - γράφεται `restore-journal.json` με τη λίστα κινήσεων·
   - τα υπάρχοντα αρχεία μετακινούνται σε `<φάκελος δεδομένων>\pre-restore-<ts>\`·
   - τα νέα μετακινούνται στη θέση τους με `os.replace` (και τα TLS στις διαδρομές `--tls-cert` / `--tls-key`)·
   - διαγραφή journal και staging.
   - Σε οποιοδήποτε σφάλμα: αυτόματη επιστροφή των αρχείων από το `pre-restore-<ts>`.
   - Αν η διαδικασία κοπεί (ρεύμα, kill), το journal μένει. Το `director.main` **αρνείται να ξεκινήσει** όσο υπάρχει journal: «Η επαναφορά διακόπηκε. Τρέξτε python -m director.backup rollback.» Το `rollback` επαναφέρει την προηγούμενη κατάσταση και είναι ασφαλές να τρέξει πολλές φορές.
6. MP3 (§5) και σύνοψη: έκδοση μητρώου, πλήθος Clients/αιτημάτων, αποτύπωμα TLS, διαδρομή `pre-restore-<ts>` με σημείωση «Περιέχει το προηγούμενο ιδιωτικό κλειδί. Σβήστε τον φάκελο αφού βεβαιωθείτε ότι όλα λειτουργούν.»
7. Μετά το restore οι Clients συνδέονται κανονικά, **χωρίς νέα εγγραφή**, επειδή ταυτότητα TLS και μητρώο είναι τα ίδια.

## 7. Χειρισμός ιδιωτικού κλειδιού (Windows)

- Το κλειδί υπάρχει χωρίς κρυπτογράφηση **μόνο** στη μνήμη και μέσα στο κρυπτογραφημένο payload. Κανένα προσωρινό plaintext αρχείο εκτός από τη θέση όπου ήδη βρίσκεται σήμερα και το staging μέσα στον ίδιο φάκελο δεδομένων.
- Το κλειδί γράφεται με `_write_secret`. Σε Windows ο φάκελος βρίσκεται στο προφίλ του χρήστη, οπότε κληρονομεί ACL (χρήστης, SYSTEM, Administrators). Ο φάκελος staging και ο `pre-restore-<ts>` δημιουργούνται **μέσα** στον φάκελο δεδομένων ώστε να έχουν το ίδιο ACL, όχι στο `%TEMP%`.
- Μετά τη χρήση, οι μεταβλητές με το κλειδί και τον κωδικό δεν κρατιούνται σε μακρόβια αντικείμενα. Η Python δεν εγγυάται μηδενισμό μνήμης, οπότε δεν γίνεται τέτοιος ισχυρισμός.
- **4.2C2 (υλοποιήθηκε 22/11/2026, `shared/manager_key.py`, αρχείο κωδικού `director-tls.key.pass`):** κρυπτογραφημένο PKCS#8 για το κλειδί TLS του Manager, με password προστατευμένο από **DPAPI CurrentUser** (ίδιο μοτίβο με το `shared/device_identity.py`) και φόρτωση με `load_cert_chain(password=…)`. Το backup περιέχει πάντα το κλειδί **ξεκλείδωτο μέσα στο κρυπτογραφημένο payload**, επειδή το DPAPI δεν μεταφέρεται σε άλλον υπολογιστή. Το restore το ξαναπροστατεύει για τον νέο υπολογιστή. Το 4.2C σχεδιάζει το βήμα εγγραφής του κλειδιού ως μία συνάρτηση, ώστε η 4.2C2 να αλλάξει μόνο αυτήν.

## 10. Αυτόματα tests (`tests/test_backup.py`)

Όλα χωρίς δίκτυο και χωρίς openssl CLI, με προσωρινούς φακέλους και χαμηλό `n` του scrypt μόνο μέσα στα tests (π.χ. `2^14` μέσω παραμέτρου συνάρτησης, όχι επιλογής CLI).

1. Round trip: create → restore σε κενό φάκελο → ίδια bytes για πιστοποιητικό, κλειδί, μητρώο, pending, last-seen, director.id, director-gui.json.
2. Λάθος κωδικός → κωδικός 3, κανένα αρχείο δεν γράφεται.
3. Αλλαγή ενός byte στην κεφαλίδα, στο ciphertext και στο tag → κωδικός 3 σε κάθε περίπτωση.
4. Κεφαλίδα με `n = 2^30` ή `r ≠ 8` → απόρριψη **πριν** από το KDF.
5. Αρχείο > 16 MiB, λάθος magic, κομμένο αρχείο → κωδικός 2.
6. `format: 2` → μήνυμα «νεότερη έκδοση».
7. Backup χωρίς προαιρετικές ενότητες → restore με προεπιλογές. Άγνωστη ενότητα → αναφέρεται και αγνοείται. Λείπει `tls_identity` ή `client_registry` → απόρριψη.
8. Κλειδί που δεν ταιριάζει με το πιστοποιητικό, ή μητρώο με άκυρη υπογραφή → απόρριψη τόσο στο create όσο και στο restore.
9. Κωδικός < 12 χαρακτήρων ή διαφορετική επιβεβαίωση → άρνηση. Ίδιος ελληνικός κωδικός σε NFC και NFD → ίδιο αποτέλεσμα.
10. Νέο salt και nonce σε κάθε backup (δύο backup των ίδιων δεδομένων διαφέρουν).
11. Restore με κρατημένο `manager.lock` → κωδικός 4.
12. Restore πάνω σε άλλη ταυτότητα → κωδικός 5. Με `--replace-identity` → επιτυχία και `pre-restore-<ts>` με τα παλιά αρχεία.
13. Παλαιότερο μητρώο και σύγκρουση → κωδικός 5. Με `--accept-older` → επιτυχία.
14. Σφάλμα που προκαλείται τεχνητά μετά από κάθε βήμα μετακίνησης → τα αρχικά αρχεία ακέραια.
15. Journal που έμεινε από διακοπή → `director.main` αρνείται να ξεκινήσει. `rollback` επαναφέρει. Δεύτερο `rollback` δεν αλλάζει τίποτα.
16. MP3: manifest σωστό. `--media-copy yes` δημιουργεί αντίγραφο με σωστά hash. Στο restore αναφέρονται «λείπει», «διαφέρει», «επιπλέον». Το `--restore-media` αντιγράφει μόνο ό,τι λείπει, ποτέ δεν αντικαθιστά.
17. Το `inspect` δεν τυπώνει «PRIVATE KEY», «CERTIFICATE» ή base64 του κλειδιού. Ο κωδικός δεν εμφανίζεται σε καμία έξοδο.
18. Μετά το restore, το `SignedClientRegistry` φορτώνει το μητρώο και ο `RegistryTrust` δίνει SSLContext που δέχεται τον εγκεκριμένο Client σε loopback mTLS (χωρίς νέα έγκριση).
19. Ο προορισμός backup δεν αντικαθίσταται αν υπάρχει. Δεν μένει `.sib.tmp` μετά από σφάλμα.

Η πλήρης σουίτα πρέπει να περνά σε Linux και Windows, χωρίς νέα `skipped` στα Windows.

## 11. Πραγματική δοκιμή (αυτόματο script, Manager σε Windows)

Χωρίς χειροκίνητα βήματα. `powershell -ExecutionPolicy Bypass -File tools\backup_live_test.ps1` στον Windows υπολογιστή του Manager (το `.sh` τρέχει τα ίδια βήματα στο Linux ανάπτυξης). Το script δουλεύει **μόνο σε προσωρινούς φακέλους** (π.χ. `%TEMP%\sch-backup-test-<ts>\pc-old` και `\pc-new`), δεν αγγίζει το πραγματικό `%USERPROFILE%\.school-intercom`, και στο τέλος τα σβήνει. Ο Manager και ο Client τρέχουν στον ίδιο υπολογιστή (loopback `127.0.0.1`, θύρες 51555/51556/51559 ώστε να μη συγκρούονται με πραγματικό Manager), επαναχρησιμοποιώντας τις βοηθητικές συναρτήσεις του `tools/mtls_live_test.py`. Τυπώνει `PASS`/`FAIL` ανά βήμα και σύνολο `N/18 PASS`, και επιστρέφει κωδικό ≠ 0 αν κάποιο αποτύχει.

1. Δημιουργία ταυτότητας TLS στο `pc-old`.
2. Εκκίνηση Manager `pc-old`, εγγραφή Client Α με κωδικό, έγκριση. Ο Client Α συνδέεται.
3. Δεύτερος Client Β εγκρίνεται και μετά ανακαλείται. Ένα τρίτο αίτημα μένει εκκρεμές.
4. Φάκελος MP3 με 2 μικρά δοκιμαστικά αρχεία.
5. `create` με Manager σε λειτουργία → επιτυχία, προειδοποίηση MP3, `--media-copy yes` → αντίγραφο με σωστά hash.
6. `inspect` χωρίς κωδικό δείχνει μόνο κεφαλίδα. Με κωδικό δείχνει 2 Clients, 1 αίτημα, 2 MP3, ίδιο αποτύπωμα TLS. Καμία εμφάνιση κλειδιού.
7. `restore` με λάθος κωδικό → κωδικός 3, ο `pc-new` μένει κενός.
8. `restore` αλλοιωμένου αντιγράφου → κωδικός 3.
9. Διακοπή Manager `pc-old`.
10. `restore` στον `pc-new` → επιτυχία. Αναφορά «λείπουν 2 MP3».
11. `restore --restore-media` → τα 2 MP3 αντιγράφονται με σωστά hash.
12. Αποτύπωμα TLS, έκδοση μητρώου, εκκρεμές αίτημα και τελευταία σύνδεση ίδια με όσα έδειξε το `inspect` του βήματος 6.
13. Εκκίνηση Manager `pc-new`. Ο Client Α συνδέεται **χωρίς νέα εγγραφή** και λαμβάνει ήχο ανακοίνωσης (όπως στο `mtls_live_test`).
14. Ο ανακλημένος Client Β απορρίπτεται και στον `pc-new`.
15. Το εκκρεμές αίτημα εγκρίνεται στον `pc-new` με τον κωδικό του.
16. `restore` ενώ τρέχει ο Manager `pc-new` → κωδικός 4.
17. Διακοπή Manager, restore με τεχνητή διακοπή στη μέση (κρυφή μεταβλητή περιβάλλοντος μόνο για scripts) → ο Manager αρνείται να ξεκινήσει. `rollback` → ο Manager ξεκινά και ο Client Α συνδέεται.
18. Restore πάνω σε υπολογιστή με άλλη ταυτότητα → κωδικός 5. Με `--replace-identity` → επιτυχία και φάκελος `pre-restore-<ts>`.

Προαιρετικά, μετά την επιτυχία των 18 βημάτων: πραγματική μεταφορά σε **δεύτερο** Windows υπολογιστή με Clients σε άλλα PC. Δεν απαιτείται για το merge του 4.2C.
