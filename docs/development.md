# School Intercom — Διαδικασία ανάπτυξης

## 1. Συνεργασία GitHub
| Branch | Σκοπός |
|---|---|
| `main` | Σταθερές εκδόσεις |
| `dev` | Κοινή βάση ενσωμάτωσης |
| `gpt-dev` | ChatGPT |
| `ai-dev` | Claude |

Τα δύο AI προτείνουν Pull Requests από το προσωπικό τους branch προς `dev`. Ο χρήστης ελέγχει/συγχωνεύει. Καμία αυτόματη συγχώνευση. Πριν από εργασία, έλεγξε τις οδηγίες του `dev`, την κατάσταση branches και τυχόν ανοιχτά PR. Μην τροποποιείς branches τρίτων ή σταθερά branches χωρίς ρητή εντολή.

## 2. Ροή εργασίας
1. Καταγραφή αιτήματος και αναγνώριση σχετικών προδιαγραφών.
2. Σύντομη ανάλυση/πρόταση και έγκριση πριν από αλλαγές κώδικα.
3. Μικρές αλλαγές στο branch του υπεύθυνου AI, χωρίς περιττά refactors.
4. Δοκιμές ανάλογα με το εύρος της αλλαγής.
5. PR προς `dev`: στόχος, αρχεία που άλλαξαν, δοκιμές, περιορισμοί και ανοιχτά ζητήματα.
6. Ο χρήστης αποφασίζει για merge, έπειτα συγχρονισμός των branches ανάπτυξης.

## 3. Φάσεις υλοποίησης
**Φάση 1 — Πρωτότυπο δύο υπολογιστών**
- Director, ένας Client, ζωντανός ήχος μέσω LAN.
- Μετρήσεις καθυστέρησης, σταθερότητας και επανασύνδεσης.
- Πρώτα λειτουργικό πρωτότυπο, όχι όλες οι δυνατότητες ταυτόχρονα.

**Φάση 2 — Πολλαπλοί Clients**
- Discovery, οργάνωση αιθουσών/Clients, συνδεσιμότητα, πολλοί Clients ανά αίθουσα.

**Φάση 3 — Διαχείριση ήχου**
- Ένταση ανά αίθουσα/Client, έλεγχος κατάστασης και ειδοποιήσεις.

**Φάση 4 — Ασφάλεια και πρόσβαση**
- Υπογραφές Director, TLS, εγγραφή/έγκριση/ανάκληση Clients.
- Το πρωτότυπο μπορεί να προηγηθεί, αλλά τα δεδομένα μαθητών και οι λειτουργίες παραγωγής δεν επιτρέπονται χωρίς τον απαραίτητο έλεγχο πρόσβασης.

**Φάση 5 — Τελική λειτουργικότητα και εγκαταστάτες**
- System Tray, single-instance και αυτόματη εκκίνηση στο Windows logon.
- Windows 10/11 installers, διατήρηση ρυθμίσεων, καταγραφή σφαλμάτων.
- Δοκιμές πιλοτικής λειτουργίας στο σχολείο.

**Επέκταση — Αμφίδρομη επικοινωνία/απουσίες**
- Μηνύματα, επιβεβαιώσεις και δηλώσεις απουσιών με τις προδιαγραφές του `requirements.md`.
- Το ακριβές στάδιο ένταξης της επέκτασης θα αποφασιστεί πριν από την υλοποίηση.

## 4. Δοκιμές
- Unit tests για πρωτόκολλο, έλεγχο χρονικών ορίων, δικαιώματα και business logic.
- Προσομοίωση πολλών Clients χωρίς πραγματικούς καταλόγους μαθητών.
- Πραγματικές δοκιμές σε Windows 10/11 για tray, συσκευές ήχου, σύνδεση LAN/Wi-Fi και installers.
- Κάθε αναφορά διαχωρίζει «δοκιμάστηκε», «ελέγχθηκε στατικά» και «δεν δοκιμάστηκε».
- Τοπική ανάπτυξη σε Linux επιτρέπεται όπου λειτουργούν οι βιβλιοθήκες, αλλά δεν υποκαθιστά τις δοκιμές Windows.

## 5. Προστασία δεδομένων και διανομή
- Δεν εισάγουμε πραγματικά προσωπικά στοιχεία μαθητών ή secrets στο repository, σε δοκιμές ή logs.
- Κώδικας και εξαρτήσεις να μπορούν να εγκατασταθούν σε τελικούς υπολογιστές χωρίς εγκατεστημένη Python.
- Οι ρυθμίσεις, τα τελικά αρχεία εγκατάστασης και η λειτουργικότητα αναβαθμίσεων ελέγχονται πριν από σχολική πιλοτική χρήση.

## 6. Κατάσταση έργου και σημείο συνέχισης — 20/11/2026

**Τρέχουσα φάση: 2 — Πολλαπλοί Clients.** Οι αλλαγές των PR #5–#10 έχουν ενσωματωθεί στο `dev`. Το PR #10 («σταθερή ταυτότητα Clients και επιλεκτική μετάδοση ανά αίθουσα») συγχωνεύτηκε στις 20/11/2026. Μετά το merge συγχρονίστηκε και το `gpt-dev` με τη βάση του `dev`. Σε νέα συζήτηση πρέπει πάντα να επανελέγχεται η *τρέχουσα* κατάσταση GitHub, όχι να θεωρείται σταθερή η παρούσα καταγραφή.

### Τι έχει υλοποιηθεί

- **Φάση 1:** εργαστηριακή μετάδοση ζωντανού μονοφωνικού PCM ήχου από Director σε Client σε LAN/TCP, 16 kHz, int16, blocks 20 ms. Υπάρχει πειραματική δοκιμή πραγματικού ήχου σε Wi-Fi/Windows· βλ. `docs/prototype.md`.
- **Μείωση καθυστέρησης (PR #7):** sequence numbers, timestamps, περιορισμένος jitter buffer και διαγνωστικές μετρήσεις· βλ. `docs/latency.md`.
- **Αξιόπιστη επανασύνδεση (PR #9):** ο Client αντιμετωπίζει διακοπή λήψης περίπου 3 s ως χαμένη σύνδεση και επιχειρεί νέα σύνδεση.
- **Πολλαπλοί Clients (PR #8):** μία λήψη μικροφώνου, ανεξάρτητη TCP αποστολή/ουρά ανά Client· ονομαστικό όριο 32 συνδέσεων. Αυτοματοποιημένοι έλεγχοι έως 20 εικονικούς Clients, όχι 20 φυσικά σχολικά PC.
- **Ταυτότητα και δρομολόγηση (PR #10):** σταθερό τοπικό UUID Client στο `~/.school-intercom/client.json`, αντιστοίχιση σε αίθουσα (`--room`), handshake κατά τη σύνδεση, επιλογή συγκεκριμένων Clients/αιθουσών από το τερματικό του Director. Οι μη επιλεγμένοι λαμβάνουν σιωπηλά PCM blocks ώστε να μη λήγει το timeout λήψης.
- **Τερματικό Director (στο PR #10):** `help`/`?`, `status`, `stats`, `stats on`, `stats off`, `all`, `none`, `room`, `client`, `quit`. Προεπιλεγμένο `stats off` για να μην κατακλύζεται η γραμμή εντολών από τις περιοδικές μετρήσεις. `stats` εμφανίζει στιγμιότυπο· `stats on` εμφανίζει μετρήσεις ανά 5 s. Η κανονική λειτουργία ήχου συνεχίζεται όταν κλείνει η εμφάνιση στατιστικών.

Τα κύρια αρχεία της Φάσης 2 είναι `director/main.py`, `director/broadcast.py`, `client/main.py`, `shared/identity.py`, `shared/audio.py`, `shared/jitter.py`, οι δοκιμές στον φάκελο `tests/` και οι οδηγίες `docs/prototype.md` / `docs/latency.md`.

### Επιβεβαιωμένοι έλεγχοι και όρια

- Ο χρήστης εκτέλεσε στο Linux `python -m unittest discover -s tests -v` και ανέφερε **35 tests / OK** πριν από τις τελευταίες αλλαγές CLI.
- Μετά την προσθήκη `help`, `stats on/off` και `quit`, ο χρήστης επιβεβαίωσε επίσης ότι **οι έλεγχοι πέρασαν**, χωρίς να δώσει νέο αριθμό tests ή αναλυτική έξοδο. Δεν πρέπει να αποδοθεί ο προηγούμενος αριθμός 35 στη νεότερη σουίτα χωρίς νέο αποτέλεσμα.
- Υπάρχουν τοπικές δοκιμές TCP/loopback και προσομοίωση πολλών Clients. **Δεν** έχει επιβεβαιωθεί πραγματική ταυτόχρονη αναπαραγωγή/επιλογή αιθουσών σε 15 σχολικούς υπολογιστές, ούτε πραγματικές επιδόσεις Ethernet/Wi-Fi με πλήρες φορτίο.
- **Δεν υπάρχει ακόμη GUI**, αυτόματη ανακάλυψη, ολοκληρωμένο heartbeat/status, κρυπτογράφηση, έγκριση Clients ή installer. Η τρέχουσα ταυτότητα είναι *αυτοδηλωμένη*, όχι ασφαλής πιστοποίηση. Μην εκτελείτε το πρωτότυπο ως παραγωγικό σχολικό σύστημα.

### Επόμενες εργασίες Φάσης 2 — προς συζήτηση/έγκριση

1. **Αυτόματη ανακάλυψη Director** στο τοπικό δίκτυο (πιθανό UDP broadcast ή mDNS/zeroconf, με χειροκίνητο `--host` ως εφεδρεία). Να συζητηθεί το ακριβές πρωτόκολλο πριν την υλοποίηση.
2. **Heartbeat και κατάσταση συνδέσεων:** αξιόπιστη εμφάνιση online/offline και βασική κατάσταση Clients, χωρίς σύγχυση με το υπάρχον timeout 3 s ή την τεχνική των σιωπηλών PCM blocks.
3. Επανεξέταση δικτυακής αποδοτικότητας: τα σιωπηλά blocks κρατούν συνδεδεμένους τους μη επιλεγμένους Clients αλλά **δεν** μειώνουν την κίνηση TCP. Αξιολόγηση μόνο με μετρήσεις· προτιμητέα ενσύρματη σύνδεση Director όταν είναι εφικτή.
4. Μετά, προετοιμασία της Φάσης 3 (διαχείριση έντασης). Το GUI και οι Windows installers είναι μεταγενέστερα στάδια σύμφωνα με τις προδιαγραφές.

### Πώς συνεχίζεται η εργασία σε νέα συζήτηση

1. Άνοιγμα του `project_instructions.md` από `dev`, έπειτα `docs/requirements.md`, `docs/architecture.md`, αυτού του αρχείου και των `docs/prototype.md` / `docs/latency.md`.
2. Έλεγχος `dev`, `gpt-dev`, `ai-dev` και εκκρεμών PR. Συγχρονισμός του `gpt-dev` μετά από merges μόνο με ασφαλή διατήρηση ιστορικού.
3. Σύντομη πρόταση για το επόμενο βήμα και **έγκριση του χρήστη πριν από αλλαγές κώδικα**.
4. Μικρές αλλαγές αποκλειστικά στο `gpt-dev`, αυτοματοποιημένοι έλεγχοι χωρίς εγκατάσταση σε σχολικούς υπολογιστές και PR προς `dev` χωρίς αυτόματο merge.
5. Για ελέγχους στο Linux: `.venv/bin/python -m unittest discover -s tests -v`. Για χειροκίνητες εντολές Director/Client: `docs/prototype.md`.

**Σημαντική πρακτική προτίμηση:** Μέχρι το σύστημα να ωριμάσει, οι δοκιμές με ~15 Clients να γίνονται κατά προτεραιότητα με εικονικούς Clients στον προσωπικό υπολογιστή ανάπτυξης· να αποφεύγεται η εγκατάσταση Python ή προσωρινών builds στους 15 σχολικούς υπολογιστές μόνο για ενδιάμεσα τεστ.
